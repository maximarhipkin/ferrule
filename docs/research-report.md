# Building a Portable, Memory-Efficient Agent OS in Rust — Multi-Model Harness Architecture for Claude, Codex, Kimi, and Beyond

**Research report — September 23, 2026**

## TL;DR

The single most important research finding: **the harness, not the model, is the performance lever.** OpenAI demonstrated that the *same* model (GPT-5.6 Sol) scored **13.3% vs 38.3%** on ARC-AGI-3 depending solely on harness configuration (retained reasoning + context compaction), while cutting output tokens roughly **6×** ([OpenAI](https://openai.com/index/introducing-the-agents-api/), [explainx.ai](https://explainx.ai/blog/codex-as-a-platform-open-agent-harness-august-2026)). So "use 100% of each model's capability" is precisely a harness-engineering problem — and Rust is the right substrate: the OpenClaw-style design has already been proven in Rust by **ZeroClaw** (<5 MB RAM, ~8.8 MB binary, <10 ms cold start, vs >1 GB RAM for the TypeScript OpenClaw). The recommended design is a **single static Rust binary** with a trait-driven plugin core (provider / channel / tool / memory), a Gateway-style control plane with per-session serialization, per-model **harness profiles** (Claude via prompt-caching breakpoints and the official CLI subprocess for subscription auth; Codex via the Responses API with retained reasoning and `/responses/compact`; Kimi via its OpenAI-compatible API with context caching and interleaved thinking), SQLite-based hybrid memory (FTS5 BM25 + vectors), on-demand skill loading, and OS-level sandboxing. One hard constraint to design around: **Anthropic subscription OAuth is legally and technically restricted to official Anthropic products** — your agent can use a Claude subscription only by driving the official `claude` CLI as a subprocess, never by extracting its token into your own HTTP client.

## 1. What you are actually building

Strip away the branding and every "agent OS" — OpenClaw, NanoClaw, ZeroClaw, Codex, Claude Code — reduces to the same four-layer system: a **control plane** that receives events and owns session state, a **harness** (agent loop) that assembles context, calls the model, and executes tools until the task terminates, a **memory layer** that persists knowledge across runs, and a **tool/sandbox layer** that gives the model safe effects on the world. The model itself is a replaceable component plugged into the harness; everything else is what you are engineering. This decomposition is not a stylistic choice — it is how the systems you admire are actually built. OpenClaw routes every message through a seven-stage pipeline (channel normalization → routing/session serialization → context assembly → model inference → ReAct loop → on-demand skill loading → memory persistence), with sessions processed one message at a time through a command queue to prevent state corruption ([freeCodeCamp](https://www.freecodecamp.org/news/how-to-build-and-secure-a-personal-ai-agent-with-openclaw/)). Claude Code's loop is a reactive ReAct loop with a five-layer compaction pipeline, a four-level `CLAUDE.md` memory hierarchy, and subagents that run in isolated context windows and return only summaries to the parent ([arXiv — The Design Space of Today's and Future AI Agent Systems](https://arxiv.org/html/2604.14228v1), [Claude Code Docs](https://code.claude.com/docs/en/how-claude-code-works)).

The practical consequence for your project: you do not need to invent an architecture. The agent-OS pattern is well documented and converged across independent teams — what differentiates a great implementation from a mediocre one is (a) how faithfully the harness matches each model's trained affordances, (b) how context is managed over long horizons, and (c) runtime discipline (memory, startup, deployability). The rest of this report mines the published architectures of OpenClaw, NanoClaw, ZeroClaw, Claude Code, Codex, and Kimi Code CLI for concrete, stealable design decisions, then assembles them into a Rust blueprint.

A second framing worth internalizing before writing code: the industry has shifted from "LLM API" to "**Harness as a Service**" — the dominant default in 2026 is to start from a runtime (Claude Agent SDK, Codex CLI as a library, OpenCode's SDK) and customize prompts, tools, and policies on top, because compaction, hooks, sandboxes, permission gates, and observability all ship with the runtime ([The Deep Feed](https://www.thedeepfeed.ai/posts/2026-05-09-agent-harness-engineering-the-discipline/)). You are building your own harness in Rust, which means you must consciously re-implement — or deliberately embed — the pieces those runtimes give away for free. The good news is that two of the three harnesses you care about are open source, and one of them (Codex) is already written in Rust and licensed Apache 2.0, making it legally embeddable as a dependency or reference implementation ([Floatboat](https://floatboat.ai/blog/codex-harness-open-source)).

## 2. Lessons from the "Claw" family: OpenClaw, NanoClaw, ZeroClaw

### 2.1 OpenClaw — the control-plane pattern

OpenClaw's core contribution is the **Gateway control plane**: a single process that binds locally, normalizes messages from 25+ channels into one message object, routes by session key, serializes each session through a lane queue, and orchestrates sub-agents. Under the Gateway, the agent runtime exists in two modes — an embedded in-process runner for light tasks, and a CLI runner that spawns external agent processes (e.g., the `claude` CLI) communicating over ACP ([稀土掘金 source-level analysis](https://juejin.cn/post/7654804766796447744)). The run lifecycle — accepted → queued → context ready → streaming → tooling → persisted — is explicitly evented, which is what makes the system observable and recoverable rather than a `while` loop you have to hope behaves ([OpenClaw Docs — Agent Loop](https://openclaw-ai.com/en/docs/concepts/agent-loop/)).

Two OpenClaw design decisions are directly relevant to your efficiency goals. First, **context assembly is treated as the most consequential engineering decision in the system**: the runtime builds the system prompt from a base prompt, a *compact skills list* (names, descriptions, and file paths only — never full content), bootstrap context files, and per-run overrides, and it enforces model-specific context limits with a **compaction reserve** — a token buffer kept free so the model never runs out of room mid-reasoning ([freeCodeCamp](https://www.freecodecamp.org/news/how-to-build-and-secure-a-personal-ai-agent-with-openclaw/)). Second, memory is **file-based and auditable**: "the workspace is the agent's long-term memory; what is on disk is what the agent knows," with bootstrap files (`AGENTS.md`, `SOUL.md`, `USER.md`, …) injected at session start and a memory subsystem combining `MEMORY.md`, date-stamped daily notes, hybrid vector+keyword retrieval, and an automatic reminder to save important notes before compaction fires ([OpenClaw Chronicles](https://openclawchronicles.com/posts/openclaw-2026-5-28-architecture-control-plane-sessions/), [arXiv design-space paper](https://arxiv.org/html/2604.14228v1)).

The cautionary side of OpenClaw is equally instructive: it has grown to nearly half a million lines of code, 53 config files, and 70+ dependencies, all running in one Node process with shared memory and application-level (not OS-level) security — the exact complexity and risk profile that motivated NanoClaw's existence ([NanoClaw GitHub](https://github.com/nanocoai/nanoclaw)). For a Rust rewrite, this validates the decision to keep the core small and push isolation down to the operating system rather than re-implementing permission checks in application code.

### 2.2 NanoClaw — minimum viable agent OS

NanoClaw proves how little code an agent OS actually needs: roughly 15 source files (~3,900 lines), fewer than 10 dependencies, zero configuration files, and one host process orchestrating per-session agent containers ([Solvea comparison](https://solvea.cx/blog/nanoclaw-vs-openclaw)). Its architecture is a queue, not a framework: `messaging apps → host router → inbound.db → container (agent runner) → outbound.db → delivery`. Each session gets two SQLite files with exactly one writer each — no IPC, no stdin piping, no cross-mount contention ([NanoClaw GitHub](https://github.com/nanocoai/nanoclaw)). That "SQLite as the message bus" pattern ports beautifully to Rust (via `sqlx` or `rusqlite`) and is far more memory-efficient than broker-based event systems.

NanoClaw also pioneered the **"best harness, best model"** stance you asked for: it natively uses Claude Code via Anthropic's official Claude Agent SDK — inheriting Claude Code's full toolset and context management — and treats every other provider as a drop-in skill (`/add-codex` for OpenAI Codex with ChatGPT subscription or API key, `/add-opencode` for OpenRouter/Google/DeepSeek, `/add-ollama-provider` for local models), configurable per agent group ([NanoClaw GitHub](https://github.com/nanocoai/nanoclaw)). The transferable insight is that provider diversity is handled at the *agent group* level, not by lowest-common-denominator abstraction: each agent gets the harness its model was trained for. Its other transferable trait is container-based security — every agent runs in its own Linux container and can only see explicitly mounted directories, so bash access is safe by construction rather than by policy ([scriptbyai](https://www.scriptbyai.com/nanoclaw-openclaw-alternative/)).

### 2.3 ZeroClaw — the existence proof for Rust

ZeroClaw is the most important data point for your project because it already demonstrates that the entire OpenClaw concept fits in a Rust binary: **~8.8 MB static binary (3.4 MB in minimal builds), <5 MB RAM, <10 ms cold start on a 0.8 GHz CPU, cross-compiled to x86/ARM/RISC-V**, versus OpenClaw's >1 GB RAM and Node.js dependency chain ([pinggy.io](https://pinggy.io/blog/zeroclaw_lightweight_openclaw_alternative/), [Techy Verse comparison](https://www.techyverse.in/blog/sohail-shaikh/openclaw-vs-zeroclaw-vs-picoclaw-vs-nullclaw-vs-nanobot-vs-tinyclaw-vs-nanoclaw-comparison)). Architecturally it is **trait-driven**: `Provider`, `Channel`, `Tool`, `Memory`, `Runtime`, `Tunnel`, and `Security` are all Rust traits, so any subsystem can be swapped without touching the others — exactly the plugin discipline your multi-model requirement demands ([AllClaw](https://allclaw.org/claw/zeroclaw)). One daemon can host multiple named agents, each with its own workspace, memory scope, model, skills, channels, and security policy ([scriptbyai](https://www.scriptbyai.com/rust-alternative-openclaw-zeroclaw/)).

ZeroClaw's memory subsystem is worth copying almost verbatim: native SQLite memory with a `sqlite-hybrid` mode combining vector similarity and FTS5 keyword search (weighted 0.7/0.3), **time-decay scoring** (evergreen "core" facts plus conversation memories with a 7-day half-life), two-phase LLM-driven consolidation (daily history summarization + core-fact extraction) at the end of each turn, and periodic hygiene every 12 hours to archive, purge, and prune ([agents-shared inventory](https://github.com/wuxxin/agents-shared)). Its security defaults — localhost binding, pairing-based auth, deny-by-default allowlists, workspace scoping, Landlock/Bubblewrap sandboxing — give you a checklist for your own `Security` trait. The honest caveat from reviewers: ZeroClaw's plugin/channel ecosystem is younger than OpenClaw's, and availability of an adapter is not the same as maturity ([MyClaw.ai](https://myclaw.ai/blog/openclaw-vs-zeroclaw)) — but for a from-scratch project, that is an argument to study its core rather than to adopt its ecosystem.

| Runtime footprint | >1 GB RAM, Node.js 22+ | Small host + Docker per agent | <5 MB RAM, ~8.8 MB binary | Rust single binary |

## 3. The harness is the product — evidence and principles

### 3.1 The ARC-AGI-3 result, and what it means for you

The strongest published evidence that harness design dominates model choice is OpenAI's ARC-AGI-3 investigation: GPT-5.6 Sol initially scored 13.3% on the public set because the harness discarded the model's private reasoning after every action and used rolling truncation once the context limit was hit — the model lost both its reasoning and parts of its interaction history. Enabling **retained reasoning** (carrying reasoning state across turns and tool calls) and replacing truncation with **compaction** (summarizing instead of deleting) raised the score to **38.3%** — nearly 3× — while cutting output-token consumption roughly **6×**, with zero changes to the model itself ([HIPTHER](https://hipther.com/latest-news/2026/07/30/115994/ai-dispatch-openai-gpt%E2%80%915-6-robo-ai-alif-holding-and-illumend-push-ai-beyond-the-model-30-july-2026/), [explainx.ai](https://explainx.ai/blog/openai-arc-agi-3-retained-reasoning-compaction-july-2026)). OpenAI's explicit recommendation for API developers is the "production triad": use the Responses API (not legacy Chat Completions), retain reasoning across turns, and use compaction instead of silent rolling truncation ([explainx.ai](https://explainx.ai/blog/openai-arc-agi-3-retained-reasoning-compaction-july-2026)).

For your agent this translates into a hard architectural rule: **the harness must be model-aware, not model-generic.** A model trained with interleaved thinking (Kimi K2 Thinking generates reasoning tokens, decides to call a tool, reasons about results, and continues — 200–300 sequential tool calls without human intervention) wastes its capability if your loop strips reasoning content between turns ([Leanware](https://leanware.co/insights/kimi-k2)). A model whose API offers server-side compaction (`/responses/compact` for GPT-5.2+) or implicit context caching (Kimi, at roughly 5× cheaper cached input) leaves money and capability on the table if your runtime doesn't use those endpoints ([OpenAI model guidance](https://developers.openai.com/api/docs/guides/model-guidance?model=gpt-5.2), [阿里云 Model Studio](https://help.aliyun.com/en/model-studio/moonshot-kimi-k2-instruct)). This is why the recommended design has a *harness router* with per-model profiles rather than one generic chat-completions loop.

### 3.2 Context engineering: the compaction playbook

Long-horizon agents accumulate histories that eventually exceed any context window, and how you shed tokens determines whether the agent keeps working or degrades into repetition. The current best practices, drawn from production harnesses and the 2026 literature, are concrete enough to implement directly. **Trigger compaction at ≈70–75% of the context window, not 95–98%** — compacting late leaves the model too few output tokens to write a good summary and produces the "context anxiety" failure mode where summaries become compressed and incomplete ([Zylos research](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)). **Use structured compaction templates**, not freeform summarization: require the summary to populate explicit sections (session intent, files modified with full paths, key decisions, active goals, next steps), which acts as a checklist and prevents silent information loss — this is the primary differentiator in Factory.ai's benchmark results ([Zylos research](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)).

Equally important is what happens *before* and *outside* compaction. Apply **deterministic cleanup first** — drop duplicate file reads keeping only the most recent, purge resolved error messages, truncate verbose API responses — which cuts context 15–30% with no information loss and no model cost ([Zylos research](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)). **Offload durable facts to external memory eagerly, at write time, not at compaction time**: architectural decisions, user preferences, and environment constants should go to structured memory files the moment they are established, because relying on retroactive extraction during compaction is fragile ([Zylos research](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)). Keep the **system prefix byte-for-byte stable across turns** and place a cache breakpoint at its end — timestamps and session IDs belong in the final user message, not the prefix; this is the single highest-ROI change for cost reduction via prompt caching ([Zylos research](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)). On the research frontier, **parallel compaction** replaces one blocking summarization call with per-block compaction, giving fine-grained, predictable control over summary volume and reducing end-to-end wall time ([arXiv 2605.23296](https://arxiv.org/abs/2605.23296)); and **adaptive compaction** applies variable compression intensity by recency — recent verbatim, intermediate lightly summarized, old noise aggressively condensed ([Manu's Vault](https://bursasiu.ro/06-Software-Engineering/Atomic/Adaptive-Context-Compaction)). For always-on agents, bounded two-tier memory (a frozen human-authored brief plus an auto-compacted rolling log, capped at ~1,500 tokens total) has been demonstrated to keep 24/7 agents stable for months ([arXiv 2604.05854](https://arxiv.org/html/2604.05854)).

## 4. Provider strategy: extracting 100% from each model

### 4.1 Claude — subscription reality and the harness to match

The Claude subscription question has a precise 2026 answer, and it constrains your design. Anthropic deployed server-side checks on January 9, 2026 that rejected subscription OAuth tokens from third-party tools, formalized in a Terms of Service update on February 17–19: **OAuth authentication is intended exclusively for Claude Code and Claude.ai; using Free/Pro/Max OAuth tokens in any other product is a ToS violation**, and the Agent SDK explicitly requires API-key authentication ([autonomee.ai](https://autonomee.ai/blog/claude-code-terms-of-service-explained/), [Bito](https://bito.ai/ai-tools/opencode-vs-claude-code-a-2026-comparison-after-the-oauth-split/)). The full cutoff for third-party tools completed around April 4, 2026; Anthropic's stated reason was that third-party harnesses bypass prompt-cache optimizations and placed disproportionate pressure on subscription compute ([apiyi.com](https://help.apiyi.com/en/anthropic-claude-subscription-third-party-tools-openclaw-policy-en.html)). A June 16, 2026 email walked back a planned migration to dedicated monthly credits — "Agent SDK, claude -p, and third-party app usage continues to work with your subscription exactly as it did before" — but the written policy restricting OAuth to official clients remains the safe interpretation, and some users report third-party OAuth usage being metered as extra-usage credits rather than subscription allowance ([hermes-agent issue #47260](https://github.com/NousResearch/hermes-agent/issues/47260)).

The compliant design that preserves your "connect my Claude subscription" feature is the **NanoClaw/GoBot pattern: drive the official `claude` CLI as a subprocess** (`claude -p "task" --output-format stream-json`), which is Anthropic's own product, remains subscription-backed on the user's own machine, and was never affected by the OAuth block ([Creeta](https://news.creeta.com/en/claude-code-oauth-block-2026-third-party-tools/), [Claude Code Docs — headless](https://code.claude.com/docs/en/headless)). In this mode your Rust binary orchestrates — session lanes, channels, memory, scheduling — while Claude Code's own harness runs the inner loop. For direct-API mode (API key, Bedrock, Vertex), your Claude harness profile should replicate what Claude Code does natively: stable system prefix with `cache_control` breakpoints, a `CLAUDE.md`-style instruction hierarchy, tool definitions deferred until needed (Claude Code defers MCP tool definitions and loads them on demand via tool search, so only names consume context), subagent delegation with isolated context windows and summary-only returns, and automatic context management that clears old tool outputs before summarizing ([Claude Code Docs](https://code.claude.com/docs/en/how-claude-code-works), [arXiv design-space paper](https://arxiv.org/html/2604.14228v1)). One more nuance for CI/server deployment: `claude --bare` skips auto-discovery of hooks, skills, MCP servers, and CLAUDE.md and never reads OAuth credentials — bare mode requires an API key, so subscription auth only works in the default (non-bare) headless mode on the user's machine ([Claude Code Docs — headless](https://code.claude.com/docs/en/headless)).

### 4.2 Codex / OpenAI — the harness is open source, and it is Rust

OpenAI is the most permissive of your three targets, and strategically the easiest to extract full capability from. On August 19, 2026, OpenAI published "Codex as a platform," formally open-sourcing the harness behind every Codex surface under Apache 2.0 in the `openai/codex` repo, and offering three integration tiers: `codex exec` (bounded one-shot jobs with structured output), the Codex SDK (start/resume/stream tasks programmatically), and the **app-server** — a documented JSON-RPC-over-stdio protocol for persistent threads, streamed events, interruption, and approval handling, deliberately backward-compatible ([explainx.ai](https://explainx.ai/blog/codex-as-a-platform-open-agent-harness-august-2026), [Enera](https://www.eneralabs.com/blog/openai-codex-harness-open-source-enterprise-2026/)). Critically for you, the core is **~96% Rust** (`codex-rs`): the `core` crate owns the agent loop and tool execution, `cli`/`tui` own the interfaces, and `headless` speaks JSON-RPC over stdio — the monorepo is intentionally consumable as a dependency ([LinkedIn/UMATR analysis](https://www.linkedin.com/posts/jai-vine_ai-dev-tooling-is-quietly-becoming-a-rust-activity-7442165593824452608-VpEG), [jidonglab source analysis](https://plzai.hashnode.dev/openai-codex-open-source-analysis)). You can therefore embed Codex's battle-tested loop in three ways: link `codex-rs` crates directly, spawn the app-server and speak its protocol, or use a library-first SDK like **nanocodex** (gakonst), which embeds the complete OpenAI Responses loop — retained sessions, typed history, tools, Code Mode, branches, retries — as a Rust library with PyO3/JS bindings, and even supports ChatGPT subscription login import with automatic account failover ([nanocodex GitHub](https://github.com/gakonst/nanocodex)).

On subscription access, OpenAI has deliberately counter-positioned against Anthropic's block: it publicly welcomed third-party tools and extended Codex subscription access to Cline, RooCode, and OpenHands, so driving Codex with a ChatGPT plan through its official auth (`~/.codex/auth.json`) is a sanctioned pattern, unlike the Claude equivalent ([Creeta](https://news.creeta.com/en/claude-code-oauth-block-2026-third-party-tools/)). For direct API mode, your Codex harness profile should implement the production triad on the Responses API: retain reasoning items across turns via `previous_response_id` chaining, and compact via `POST /responses/compact` — which returns encrypted, opaque items that preserve task-relevant information — after major milestones rather than every turn, keeping prompts functionally identical when resuming to avoid behavior drift ([OpenAI model guidance](https://developers.openai.com/api/docs/guides/model-guidance?model=gpt-5.2), [GPT-5.2 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-2_prompting_guide)). The ARC-AGI-3 numbers in Section 3 are, in effect, the datasheet for why this profile must exist.

### 4.3 Kimi — OpenAI-compatible surface, agentic-native internals

Kimi is the friendliest target technically: Moonshot's API is **OpenAI SDK-compatible** (change base URL and key), and the K2 family was explicitly trained for agentic workloads — K2 Thinking sustains 200–300 sequential tool calls via interleaved thinking, where reasoning and acting form one continuous loop rather than separate phases ([Leanware](https://leanware.co/insights/kimi-k2), [WaveSpeedAI](https://wavespeed.ai/llm/moonshotai/kimi-k2-thinking)). The current lineup your model router should know: **kimi-k2.6** (general-purpose, 256K context, text/image/video input, thinking and non-thinking modes), **kimi-k2.7-code** (coding-tuned, thinking always on, 256K context, ~33K max output), and **Kimi K3** (newer flagship with a 1M-token context and always-on reasoning) ([Chatbase](https://www.chatbase.co/blog/kimi-k2-api), [TokenMix](https://tokenmix.ai/models/moonshot/kimi-k2.7-code)). Pricing is aggressive — roughly $0.60/1M input and $2.50–3.00/1M output for K2.x, with **context caching supported** (cached input around 5× cheaper, e.g. ¥0.8–1 vs ¥4 per million tokens), which makes the cache-stable-prefix discipline from Section 3.2 directly profitable on this provider ([Requesty](https://www.requesty.ai/models/moonshot/kimi-k2-5), [阿里云 Model Studio](https://help.aliyun.com/en/model-studio/moonshot-kimi-k2-instruct)).

Your Kimi harness profile should preserve thinking content across tool calls (interleaved thinking is the trained behavior — stripping it is the Kimi equivalent of OpenAI's ARC-AGI-3 mistake), lean on its long context to defer compaction later than you would for smaller-window models, and exploit native tool-calling with streaming. Moonshot also ships **Kimi Code CLI** (MIT-licensed, TypeScript, single binary, ACP-compatible, with built-in `coder`/`explore`/`plan` subagents) — both a reference harness for how Moonshot itself drives these models and an optional subprocess driver analogous to the Claude CLI pattern; its OAuth login state is already shared with third-party integrations in the wild ([Kimi Code CLI GitHub](https://github.com/MoonshotAI/kimi-code), [MarkTechPost](https://www.marktechpost.com/2026/06/06/moonshot-ai-releases-kimi-code-cli-a-terminal-ai-coding-agent-built-in-typescript-for-next-gen-agents/), [CordisPlugin kimi-tide](https://cordisplugin.com/plugins/tafcear-kimi-tide)). Note that K2 models do not support OpenAI-style structured outputs on all routes, so your profile should fall back to JSON-mode or prompt-based schemas where needed ([阿里云 Model Studio](https://help.aliyun.com/en/model-studio/moonshot-kimi-k2-instruct)).

### 4.4 Any other model — the generic fallback layer

For "any model I have," the industry-standard escape hatch is an **OpenAI-compatible provider trait**: DeepSeek, GLM, Gemini (via compatibility endpoints), OpenRouter, Groq, Together, and local servers (Ollama, llama.cpp, vLLM) all speak it, and Rig alone already unifies 20+ providers behind a trait-based interface with one-line swapping ([Zylos Rust landscape](https://zylos.ai/research/2026-03-31-rust-ai-agent-frameworks-infrastructure/)). The design principle from NanoClaw applies: the generic layer is for coverage, and per-model harness profiles are for capability — never let the lowest common denominator (plain chat-completions without reasoning retention, caching, or native compaction) become the ceiling for your flagship models.

## 5. Recommended architecture: "AgentRust"

![Target architecture: channels and scheduler feed a Gateway control plane with session lanes; a harness router selects per-model profiles (Claude / Codex / Kimi drivers); a ReAct core dispatches built-in tools, MCP tools, and on-demand skills; SQLite hybrid memory and JSONL transcripts persist state; OS-level sandboxing bounds every tool run](docs/assets/chart-architecture.png)

### 5.1 Crate layout and core traits

Structure the project as a Cargo workspace with a small, stable core and everything else behind traits — the pattern ZeroClaw validates and Rig demonstrates at the provider layer. A pragmatic layout: `agentrust-core` (event types, session model, message/transcript schema, the agent loop), `agentrust-gateway` (control plane: routing, session lanes, auth, lifecycle event bus), `agentrust-providers` (one module per harness profile: `claude_api`, `claude_cli`, `codex_responses`, `codex_appserver`, `kimi`, `openai_compat`), `agentrust-tools` (built-in fs/shell/web/git tools with JSON Schema definitions derived via `schemars`), `agentrust-mcp` (MCP client on the official Rust SDK `rmcp`, which supports stdio, SSE, and Streamable HTTP transports and the Tasks extension for long-running tool invocations), `agentrust-memory` (SQLite store), and `agentrust-cli` / `agentrustd` (binary entry points) ([modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk), [rustify MCP guide](https://rustify.rs/articles/rust-for-mcp-model-context-protocol-servers-2026)).

The trait surface should be exactly the seams where reality varies: `Provider` (streaming completion with tool calls, reasoning retention, caching hints, compaction support), `HarnessProfile` (system-prompt dialect, tool-schema dialect, compaction policy, cache strategy, max context, output reserve), `Channel` (inbound normalization + outbound delivery), `Tool` (schema + sandboxed execution), `Memory` (write/recall/consolidate), and `Sandbox` (per-platform isolation backend). Keep the loop itself provider-agnostic: it consumes a stream of typed events (`text_delta`, `tool_call`, `reasoning`, `usage`, `done`) and emits lifecycle events, mirroring the OpenClaw run lifecycle (accepted → queued → context ready → streaming → tooling → persisted) so observability is structural rather than bolted on ([OpenClaw Docs — Agent Loop](https://openclaw-ai.com/en/docs/concepts/agent-loop/)).

### 5.2 The agent loop and session discipline

Adopt NanoClaw's queue discipline with OpenClaw's lifecycle visibility. Each session owns a lane: runs for the same session are serialized (preventing transcript corruption and tool races), while different sessions run concurrently across tokio tasks. Persist every event to an append-only JSONL transcript per session — this is what makes sessions resumable, forkable, rewindable, and auditable (Claude Code writes each message, tool use, and result to plaintext JSONL under `~/.claude/projects/` for exactly these properties) ([Claude Code Docs](https://code.claude.com/docs/en/how-claude-code-works)). SQLite serves double duty as both the message queue between control plane and runners (one writer per file, as NanoClaw's `inbound.db`/`outbound.db` pattern proves) and the session-state store ([NanoClaw GitHub](https://github.com/nanocoai/nanoclaw)).

The loop body per turn: assemble context (stable system prefix + harness-profile instructions + memory recall within a token budget + session history + tool schemas, with a compaction reserve kept free), call the provider through its profile, stream events, execute tool calls through the sandbox with approval gates, append results, and repeat until text-only completion, timeout, or abort. Build **subagents** as first-class: spawn them with isolated context windows and return only summaries to the parent — Claude Code's sidechain design shows this is the critical context-conservation choice, since sharing full transcripts between agents risks context explosion (its agent teams consume ~7× the tokens of a standard session even with isolation) ([arXiv design-space paper](https://arxiv.org/html/2604.14228v1)). Add hard guardrails that production harnesses converged on: max-iteration limits, per-run timeouts, a hard stop when all tools in a turn are blocked (prevents infinite token-burning cycles), and message queuing so users can submit while the agent is busy ([rustify Rust agents guide](https://rustify.rs/articles/rust-ai-agents-from-scratch-2026), [KimiFlare](https://github.com/sinameraji/kimiflare)).

### 5.3 Memory: SQLite hybrid store with decay and eager writes

The 2026 consensus for local-first agent memory is a **single SQLite file** doing double duty: FTS5 (BM25) for keyword recall plus an embedded vector index for semantic recall, merged with a weighted hybrid (ZeroClaw uses 0.7 vector / 0.3 FTS5), temporal decay so recent context outranks stale history, and a token-budgeted assembly step at session start (pinned memories first, then recent, then query-matched) ([agents-shared](https://github.com/wuxxin/agents-shared), [memweave](https://levelup.gitconnected.com/memweave-zero-infra-ai-agent-memory-with-markdown-and-sqlite-no-vector-database-required-cf3869efc840), [Agent Memory](https://klymentiev.com/projects/agent-memory)). Layered escalation stays available: local SQLite always on, optional external vector DB (Qdrant — itself Rust, or LanceDB embedded) for large corpora, optional MCP for external knowledge sources, without rearchitecting ([OpenClaw community memory guide](https://openclaw-ai.net/en/blog/ai-agent-memory-systems-2026)).

Two operational rules come straight from the compaction research. Write durable facts to memory **eagerly at the moment they are established** (decisions, preferences, environment constants), not retroactively at compaction time; and run **consolidation as a background job** — ZeroClaw's two-phase design (daily history summarization plus core-fact extraction at turn end, with 12-hour hygiene to archive/purge/prune) and OpenClaw's pre-compaction "save important notes" reminder are both proven shapes ([agents-shared](https://github.com/wuxxin/agents-shared), [arXiv design-space paper](https://arxiv.org/html/2604.14228v1)). For embeddings, prefer a local model (e.g., nomic-embed via candle/mistral.rs or an Ollama endpoint) so memory stays private and free; cache embeddings so only changed content hits the embedder ([sqlite-memory](https://github.com/sqliteai/sqlite-memory), [rust-lang forum](https://users.rust-lang.org/t/rust-for-ai-agents/136946)).

### 5.4 Tools, skills, and sandboxing

Built-in tools (file read/write/edit, grep/glob, shell, git, web fetch/search) should be defined once with `schemars`-derived JSON Schemas and rendered per provider by the harness profile — Anthropic-style `input_schema` vs OpenAI-style `function.parameters` — since tool-schema dialect is a real per-model difference. Everything beyond the built-ins should arrive through **MCP**: the official Rust SDK (`rmcp`) gives you client and server implementations with macro-based tool registration and stdio/HTTP transports, so your agent can consume the entire MCP ecosystem (and you can also *expose* your agent as an MCP server or ACP agent for editors — ACP is now supported by 17+ agents and most major IDEs) ([modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk), [掘金 ACP analysis via Kimi CLI evolution](https://juejin.cn/post/7663685196478758962)). Follow Claude Code's economy of context for tools and skills alike: advertise names and descriptions, load full schemas/skill bodies **on demand** — MCP tool definitions are deferred by default in Claude Code and only consume context when used, and OpenClaw injects only a compact skills list with file paths ([Claude Code Docs](https://code.claude.com/docs/en/how-claude-code-works), [freeCodeCamp](https://www.freecodecamp.org/news/how-to-build-and-secure-a-personal-ai-agent-with-openclaw/)).

For security, take NanoClaw's stance (isolation beats permission checks) and implement it the Rust way: run untrusted tool execution under OS sandboxing — Landlock or Bubblewrap on Linux, Seatbelt on macOS, job objects on Windows — with workspace scoping and deny-by-default shell allowlists, exactly ZeroClaw's backend strategy ([agents-shared](https://github.com/wuxxin/agents-shared)). Optional **WASM plugins** (wasmtime) give you a portable sandbox for community-contributed tools that can't touch the host at all — the approach IronClaw uses for its tool execution ([QbitNeural claw-space overview](https://qbitneural.com/nanoclaw-vs-openclaw/)). Bind the gateway to localhost by default, use pairing-based authentication, and treat skills as untrusted code to review before install — OpenClaw's own hardening checklist is directly applicable ([freeCodeCamp](https://www.freecodecamp.org/news/how-to-build-and-secure-a-personal-ai-agent-with-openclaw/)).

### 5.5 Memory efficiency and "deploy anywhere"

Rust earns its keep here through concrete, measurable techniques rather than vibes. The footprint targets are proven achievable: ZeroClaw holds idle RSS under 5 MB in a ~8.8 MB binary with sub-10ms cold starts ([pinggy.io](https://pinggy.io/blog/zeroclaw_lightweight_openclaw_alternative/)). To hit similar numbers: use **tokio with a bounded task set** (session lanes as tasks, not threads per connection), streaming HTTP/SSE parsing without buffering whole payloads, `rustls` instead of OpenSSL for portable static builds, SQLite (bundled) instead of any external service, `mimalloc` or `jemalloc` for allocation-heavy workloads, and aggressive release profiles (`opt-level = "z"` or `3`, `lto = "fat"`, `codegen-units = 1`, `strip = true`, `panic = "abort"` where acceptable) with feature-gated channel adapters so users compile in only what they need — ZeroClaw's feature-gated build model keeps prebuilt binaries lean while niche channels (Slack, Matrix, WhatsApp) stay source-build options ([scriptbyai](https://www.scriptbyai.com/rust-alternative-openclaw-zeroclaw/)).

Deployment becomes literally `scp` + run: a single static binary targeting x86_64, aarch64, ARM, and even RISC-V covers laptops, VPSs, Raspberry Pi-class SBCs, and embedded gateways — the exact "deploy anywhere" surface you asked for ([AllClaw](https://allclaw.org/claw/zeroclaw)). Keep the token-cost side of efficiency in the runtime too: model routing (cheap models for heartbeats and summarization, frontier models for hard reasoning), cache-stable prefixes, proactive tool-result dedup (15–30% context savings for free), and per-session usage accounting written into transcripts — the harness, not willpower, is what keeps an always-on agent's operating cost in the $5–50/month self-hosted band rather than the $300–750 band reported for heavy OpenClaw deployments ([Zylos](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/), [QbitNeural](https://qbitneural.com/nanoclaw-vs-openclaw/)).

## 6. Build order

Sequencing matters because each layer de-risks the next. **Phase 1 — the loop**: `core` + one provider (`openai_compat`, since it covers Kimi, DeepSeek, OpenRouter, and local models on day one) + three built-in tools (fs, shell, web) + JSONL transcripts + a CLI channel. This alone is a working agent and is essentially the rig-free "agent from scratch" pattern — LLM call, parse tool calls, execute, feed back, repeat with a max-iteration cap ([rustify](https://rustify.rs/articles/rust-ai-agents-from-scratch-2026)). **Phase 2 — the harness profiles**: add the Codex profile (Responses API with retained reasoning and `/responses/compact`) and the Claude API profile (cache breakpoints, tool-search-style deferred schemas); implement the compaction engine (70–75% threshold, structured templates, deterministic pre-cleanup); add the Kimi profile's thinking retention and context caching. **Phase 3 — the OS**: gateway with session lanes and lifecycle events, SQLite hybrid memory with decay and consolidation, skills with on-demand loading, MCP client via `rmcp`, cron/heartbeat scheduler. **Phase 4 — subscription modes**: `claude -p` subprocess driver (stream-json in/out, session resume via `--continue`), Codex app-server or nanocodex embedding for ChatGPT-login users. **Phase 5 — hardening and reach**: OS sandboxes per platform, approval UX, WASM plugin sandbox, feature-gated channels, cross-compiled release binaries.

Two anti-patterns to actively resist, both documented in the research. Do not build one generic chat-completions loop and treat providers as interchangeable — that is the failure mode the ARC-AGI-3 result quantifies ([HIPTHER](https://hipther.com/latest-news/2026/07/30/115994/ai-dispatch-openai-gpt%E2%80%915-6-robo-ai-alif-holding-and-illumend-push-ai-beyond-the-model-30-july-2026/)). And do not extract Claude OAuth tokens into your own HTTP client to "use the subscription" — it is a ToS violation that Anthropic enforces server-side; the subprocess-driver pattern gives users the subscription path legitimately ([Claude Code Docs — legal](https://code.claude.com/docs/en/legal-and-compliance), [autonomee.ai](https://autonomee.ai/blog/claude-code-terms-of-service-explained/)).

## 7. Decision summary

| Decision | Recommendation | Basis |
|---|---|---|
| Language/runtime | Rust, tokio, single static binary | ZeroClaw footprint proof; codex-rs precedent |
| Core architecture | Gateway-lite control plane + serialized session lanes + evented run lifecycle | OpenClaw 7-stage loop; NanoClaw SQLite queues |
| Model abstraction | `Provider` trait + per-model `HarnessProfile` (not a generic loop) | ARC-AGI-3: harness = 3× score, 6× tokens |
| Claude subscription | Drive official `claude` CLI subprocess (`-p`, stream-json) | Anthropic ToS blocks third-party OAuth |
| Claude API | Prompt-cache breakpoints, deferred tool schemas, subagent summary-return | Claude Code internals |
| Codex | Responses API + retained reasoning + `/responses/compact`; optional codex-rs/app-server/nanocodex embed | OpenAI open-harness platform |
| Kimi | OpenAI-compatible API, thinking retention, context caching; route K2.6/K2.7-code/K3 by task | Moonshot API surface |
| Memory | SQLite hybrid (FTS5 + vector, 0.7/0.3), time decay, eager writes, 12h hygiene | ZeroClaw/memory-ecosystem consensus |
| Context management | Compact at 70–75%, structured templates, deterministic dedupe first, stable prefixes | Production compaction playbook |
| Tools/skills | Built-ins + MCP (`rmcp`) + on-demand skill bodies | Claude Code/OpenClaw context economy |
| Security | OS sandbox (Landlock/Bubblewrap/Seatbelt), workspace scoping, localhost+pairing default | NanoClaw/ZeroClaw isolation model |
| Efficiency | Feature-gated builds, LTO/strip, local embeddings, model routing, usage accounting | <5 MB RAM / ~9 MB binary is proven |
